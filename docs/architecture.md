# Architecture: personal workout tracker (a rebuild of Hevy's core features)

Scope: the 42 buildable rows in `features.csv`. Single user to start. Web app that installs on a phone's home screen.
Written: 2026-10-22. Reads: `recon.md`, `features.csv`.

## Provenance and testing of the schema

`schema.sql` was already in `replica/` when this step started and **I did not write it**. I don't know its origin. I read all of it, scanned it for network, role and file statements (none), then loaded it into a real Postgres 16 and ran 20 checks as a restricted role so row-level security applied. All 20 pass:

- no caps: 50 routines, 60 custom exercises and 400 workouts (many older than 3 months) all insert fine
- user B sees none of user A's routines, workouts or custom exercises, cannot insert rows owned by A, cannot attach an exercise to A's routine or workout, cannot update A's routine, and `previous_sets` does not leak A's history
- built-in exercises cannot be renamed or deleted by a user
- an exercise with history cannot be deleted, a routine can be deleted without touching past workouts, and duplicate custom exercise names are blocked
- `previous_sets` returns the latest earlier workout and ignores sets that were never completed
- re-saving a workout with the same client-generated id does not duplicate it
- sign-up creates the profile row

Re-run: `replica/tests/` (`stub_auth.sql` fakes Supabase's auth schema, then `schema.sql`, then `rules_test.sql`). The stand-in `auth` is not real Supabase, so repeat a login test on the real project once it exists.

**Known gaps in the schema (not bugs, but not done):**
- No built-in exercises are seeded. We write that list ourselves (text only; Hevy's library and videos are theirs).
- No PR (personal record) logic. Compute it at read time from `workout_sets`, so editing an old workout stays correct. No separate PR table.
- `workout_sets` and `workout_exercises` have no `updated_at`. Fine for now, but it matters if sync is added later.
- `workouts.ended_at` is `not null`, so an unfinished workout cannot live in the database. See the first "part that bites".

## Stack

| layer | choice | why |
| --- | --- | --- |
| web | Next.js (App Router) + TypeScript, installable as a PWA | one codebase for phone and desktop, and the most documented stack, which matters when you can't read the code |
| styling | Tailwind | tokens come from `replica-design` |
| database | Postgres on Supabase | the schema already targets it, and row-level security means the database enforces who sees what |
| auth | Supabase Auth (email) | same project, no extra service |
| payments | none | personal use, everything unlocked |
| email | none | no emails needed |
| jobs | none to start | see "keep-alive" below |
| files | Supabase Storage, Phase 3 only | progress photos |
| hosting | Vercel Hobby | free, and its terms limit it to non-commercial personal use, which matches this project |

One database, no separate backend server. The browser talks to Supabase directly and row-level security does the authorisation. That keeps the number of moving parts you must understand to a minimum.

**Free-tier facts, checked 2026-10-22:**
- Supabase free: 500 MB database, 2 active projects, and "Free projects are paused after 1 week of inactivity." A gym app used a few times a week will rarely hit that, but a holiday will. A paused project needs a manual restart. Source: https://supabase.com/pricing
- Vercel Hobby: non-commercial personal use only. If this ever becomes a product you sell, you move to Pro. Source: https://vercel.com/docs/plans/hobby
- I did not find or verify anything about Supabase backups on the free plan. **Export your data regularly** (CSV from the app) until that is confirmed.

## Schema

Tables: 11 (`profiles`, `exercises`, `routine_folders`, `routines`, `routine_exercises`, `routine_sets`, `workouts`, `workout_exercises`, `workout_sets`, `body_measurements`, `progress_photos`). Access rules: Postgres row-level security on every table, plus composite foreign keys so one user's rows can never link to another's. SQL in `schema.sql`.

Decisions in it that matter:
- Weights are stored in kg and converted for display. Converting lb to kg to lb at 2 decimals can show 134.99 for 135, so display to 1 decimal or the nearest 0.5.
- Routines are copied into a workout when it starts, so editing a routine later never changes old workouts.
- A workout's id is generated by the phone, so a retry after a bad connection saves once. The app must save with "insert, ignore if it exists" semantics.
- Deleting an exercise that has history is blocked. The app should archive it instead.

## API

Most of this is direct table access from the app under row-level security. Only the rows marked "function" or "server" need custom code.

| method path | does | who | input | output | flow |
| --- | --- | --- | --- | --- | --- |
| auth sign-up / sign-in / sign-out | account | anyone | email, password | session | F01 |
| select routines, routine_folders | list My Routines | owner | none | rows | F01 |
| insert/update/delete routine, folder | build and edit routines | owner | fields | row | F02 |
| insert/update/delete routine_exercises, routine_sets | edit routine content | owner | fields | row | F02 |
| select exercises (search, muscle filter) | exercise picker | owner + built-ins | text, muscle | rows | F01, F02 |
| insert/update exercises (custom, archive) | custom exercises | owner | fields | row | F02 |
| function `previous_sets(exercise_id, before)` | "last time" values | owner | exercise, time | sets | F01 |
| insert workout + workout_exercises + workout_sets, one transaction | save finished workout | owner | whole workout, client id | ok | F01, F03 |
| select workouts (paged, by date) | history, calendar | owner | range | rows | F04 |
| update/delete workout and children | edit or delete past workout | owner | fields | row | F05 |
| insert routine from a workout | save as routine | owner | workout id | routine | F03 |
| select aggregates (per-exercise best, volume, sets per muscle per week) | graphs, PRs, stats | owner | exercise, range | numbers | F04 |
| upsert body_measurements | log weight and measurements | owner | kind, value, date | row | F06 |
| server: export all my data as CSV | backup | owner | none | file | none |

Webhooks: none. Jobs: none, except an optional keep-alive (see below).

## The parts that bite

- **The live workout is not in the database until you finish.** `ended_at` is required, so a half-finished workout exists only in the browser. If the tab is closed, the phone locks or the battery dies mid-session, you lose the workout unless the app saves a draft to the browser's local storage (IndexedDB) after every set and restores it on reopen. This is the most important feature after "log a set," and it is easy to forget.
- **Gyms have bad signal.** Logging has to work offline and save when the connection returns. Sync conflicts are rare with one user on one phone, but use client ids and "ignore if exists" so a retry never duplicates.
- **PRs and "previous values" change when you edit history.** Compute them from the data each time instead of storing them.
- **Time zones.** Times are stored in UTC. The calendar groups workouts by the day in `profiles.timezone`, so a late workout does not land on the wrong day. Daylight saving changes the same workout's local time, not its stored time.
- **lb versus kg display rounding** (above).
- **Pausing.** After 1 week of no use the database pauses. Fix: use the app weekly, or a free scheduled ping later (GitHub Actions or Vercel Cron).
- **Search.** With about 60 custom exercises plus our built-ins, a plain text search is fine. No search service.
- **Realtime, multi-tenancy, email deliverability:** not needed.

## Build order

1. **Vertical slice (proves the stack).** S01 sign-in, S02 workout tab, S03 routine editor (one exercise, a few sets), S04 live workout, S06 save, S07 history list. Tables: `profiles`, `exercises` (a few seeded), `routines`, `routine_exercises`, `routine_sets`, `workouts`, `workout_exercises`, `workout_sets`. Plus the draft-save of an unfinished workout. Done when you can create a routine, run it on your phone, close the tab mid-workout, reopen and finish it, and see it in history.
2. **Must-haves (17).** Add: folders, edit/delete routines and workouts, empty workout, full set types, rest timer, previous values, save as routine, exercise picker and custom exercises, unlimited history. Screens S02-S08. At the end of this step you have what you wanted at the start: unlimited routines.
3. **Should-haves (11).** RPE, supersets, exercise notes, copy workout, calendar, per-exercise graph, PRs, sets per muscle per week, body measurements, units, offline sync. Screens S09-S12, S14.
4. **Could-haves (14),** in the order you care about them. Progress photos, sharing, the generated program and Strava each add real cost or accounts, so decide on each one when we get there.
5. **Fixes from `replica-entrepreneur`,** if it finds anything worth doing. For a personal tool, it is optional.
